# DATAFENCE — MASTER ENGINEERING PROMPT

You are building **DataFence**, an open-source developer infrastructure library that creates a deterministic security and trust boundary between probabilistic AI/LLM agents and enterprise data systems.

This is not a chatbot wrapper.

This is not another prompt-injection detector.

This is not an LLM output moderation library.

This is not an LLM-as-a-judge system.

The fundamental idea is:

> **LLMs can reason probabilistically. Access to enterprise data must remain deterministic.**

DataFence sits between an AI agent and the data/action layer and enforces policies before anything reaches the underlying system.

---

# 1. PRODUCT VISION

Build a Python-first library that developers can install with:

```bash
pip install datafence
```

and put between:

```text
LLM / Agent / MCP Client
          ↓
      DataFence
          ↓
Enterprise Data / APIs / Actions
```

The LLM may propose:

* a query
* a data request
* an action
* a transformation
* an analysis

But the LLM does NOT receive direct authority to execute that request.

DataFence becomes the enforcement boundary.

The central principle:

> **The model proposes. DataFence decides.**

The model should never be able to bypass DataFence policy simply by generating different text, SQL, JSON, tool calls, or arguments.

---

# 2. CORE PROBLEM

Enterprise organizations want to use LLMs against sensitive data.

Examples:

```text
Bank transaction data
Customer records
Credit information
Insurance data
Healthcare records
Internal financial data
Employee data
Production databases
S3 data lakes
Data warehouses
Internal APIs
```

But LLMs are probabilistic.

An LLM can:

* hallucinate
* generate incorrect SQL
* request unauthorized columns
* access an incorrect dataset
* expose PII
* cross tenant boundaries
* misinterpret identity
* generate destructive operations
* manipulate tool parameters
* attempt prompt injection
* misunderstand policy
* return claims unsupported by source data

Therefore we need a deterministic layer.

DataFence should provide that layer.

---

# 3. WHAT DATAFENCE GUARANTEES

Do NOT claim:

> "DataFence makes LLMs accurate."

That is impossible.

Do NOT claim:

> "DataFence prevents hallucinations."

That is also too broad.

Instead DataFence guarantees deterministic enforcement around the operations it controls.

For example:

```text
✓ Policy enforcement
✓ Authorization enforcement
✓ Dataset restrictions
✓ Field/column restrictions
✓ Query validation
✓ Operation restrictions
✓ Tenant isolation
✓ PII handling
✓ Result validation
✓ Provenance
✓ Auditability
✓ Evidence generation
✓ Deterministic execution controls
```

The LLM can still reason incorrectly.

But it should not be able to violate the configured data-access boundary.

# 6. CORE CONCEPTS

Define these concepts explicitly in the codebase.

## Actor

Who is making the request?

Examples:

```text
human:user_123
agent:finance_assistant
service:risk_engine
application:customer_support
```

---

## Intent

What does the actor want to do?

Example:

```json
{
  "action": "read",
  "resource": "transactions",
  "subject": {
    "customer_id": "123"
  },
  "filters": {
    "date_from": "2026-09-01",
    "date_to": "2026-09-30"
  }
}
```

Do not blindly trust arbitrary natural-language intent.

Natural language may be converted into a structured intent, but DataFence must validate the structured request.

---

## Resource

A controlled enterprise resource.

Examples:

```text
transactions
customers
accounts
payments
loans
documents
s3://bucket/path
postgres://database/table
athena://catalog/database/table
```

---

## Policy

A deterministic rule defining what is allowed.

Example:

```yaml
name: bank_transactions

resources:

  transactions:

    operations:
      - read

    fields:
      allowed:
        - transaction_id
        - customer_id
        - merchant
        - amount
        - currency
        - timestamp

      denied:
        - card_number
        - cvv
        - full_account_number

    limits:
      max_rows: 10000
      max_date_range_days: 90
```

---

## Decision

Every request should result in an explicit decision.

Possible decisions:

```text
ALLOW
DENY
REDACT
REQUIRE_APPROVAL
```

Do not reduce everything to a boolean.

---

# 7. POLICY ENGINE

The policy engine is one of the most important components.

Policies must be:

* deterministic
* testable
* composable
* inspectable
* versionable
* independent from the LLM

Example:

```yaml
version: "1"

policy:
  name: banking-data

resources:

  transactions:

    allow:
      operations:
        - read

    deny:
      operations:
        - insert
        - update
        - delete

    fields:
      allow:
        - transaction_id
        - merchant
        - amount
        - currency
        - timestamp

      deny:
        - card_number
        - cvv
        - account_number

    constraints:
      max_rows: 1000
      max_date_range_days: 90
```

DataFence should load and validate this policy.

Invalid policies must fail fast.

---

# 8. POLICY EVALUATION

Create a deterministic policy evaluator.

Conceptually:

```python
decision = policy_engine.evaluate(request)
```

It should produce something like:

```python
Decision(
    status=DecisionStatus.ALLOW,
    reasons=[],
    policy_version="1",
    checks=[
        ...
    ]
)
```

For denial:

```python
Decision(
    status=DecisionStatus.DENY,
    reasons=[
        "field 'card_number' is not permitted"
    ]
)
```

Every decision should be explainable.

---

# 9. QUERY FIREWALL

This is extremely important.

Do NOT allow an LLM to freely execute arbitrary SQL.

Bad:

```python
db.execute(llm_generated_sql)
```

Instead:

```python
datafence.execute(
    request
)
```

DataFence should:

1. Parse the request
2. Validate syntax
3. Identify referenced resources
4. Identify referenced columns
5. Identify operations
6. Evaluate policy
7. Apply limits
8. Validate filters
9. Execute only if permitted
10. Validate the result
11. Generate provenance
12. Generate audit information

For SQL connectors, use a proper SQL parser.

Do NOT implement SQL parsing using regex.

---

# 10. SQL SECURITY

Support at least:

```text
SELECT
WHERE
GROUP BY
ORDER BY
LIMIT
aggregations
joins
```

but explicitly control:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
TRUNCATE
CREATE
GRANT
REVOKE
```

Default behavior should be:

> deny dangerous operations unless explicitly enabled.

Never use:

```text
SELECT *
```

when a policy specifies allowed fields.

DataFence should ideally rewrite or construct a safe query rather than simply trusting the original query.

---

# 11. COLUMN-LEVEL SECURITY

Example policy:

```yaml
fields:
  allowed:
    - customer_id
    - merchant
    - amount

  denied:
    - card_number
    - cvv
    - ssn
```

LLM request:

```sql
SELECT customer_id, card_number
FROM transactions
```

Result:

```text
DENIED

Reason:
column card_number is prohibited by policy bank_transactions:v3
```

Do not send the prohibited data to the LLM before detecting this.

---

# 12. ROW-LEVEL SECURITY

Support policies such as:

```yaml
row_filter:
  customer_id: "{{ actor.customer_id }}"
```

or:

```yaml
row_filter:
  region: "{{ actor.region }}"
```

Example:

Agent A:

```text
customer_id = 123
```

must not be able to request:

```text
customer_id = 456
```

by simply changing a parameter.

Tenant isolation must be enforced inside DataFence.

---

# 13. TENANT ISOLATION

Design for multi-tenant environments.

A request should carry context:

```python
RequestContext(
    tenant_id="bank_a",
    actor_id="agent_123",
    actor_type="agent"
)
```

A tenant must never be able to access another tenant's data through an LLM-generated query.

This must be enforced at the execution boundary.

---

# 14. PII / SENSITIVE DATA

Build a pluggable detection/redaction layer.

Initial detectors can include:

```text
Email
Phone
Credit card
SSN-like identifiers
Bank account identifiers
API keys
Secrets
```

But don't pretend regex alone provides complete PII detection.

Create an abstraction:

```python
class SensitiveDataDetector:
    def detect(self, value, context):
        ...
```

Support:

```text
ALLOW
REDACT
DENY
```

Example:

```text
4111111111111111
```

could become:

```text
4111********1111
```

depending on policy.

---

# 15. RESULT VALIDATION

Do not stop after validating the request.

Validate the returned result.

Example policy:

```yaml
result:
  max_rows: 1000
  allowed_fields:
    - transaction_id
    - amount
    - merchant
```

If a connector unexpectedly returns:

```text
account_number
```

DataFence must detect it before returning the result to the caller.

---

# 16. PROVENANCE

Every successful operation should produce provenance.

Example:

```json
{
  "source": "athena",
  "catalog": "bank",
  "database": "transactions",
  "table": "transactions",
  "policy": "banking-data",
  "policy_version": "3",
  "query_hash": "sha256:...",
  "timestamp": "...",
  "actor": "agent:finance-assistant"
}
```

Do not necessarily store raw sensitive data in audit logs.

The system should favor hashes, identifiers, metadata, and references.

---

# 17. EVIDENCE / PROOF

This is one of the core differentiators.

Every successful execution should be capable of producing an evidence object.

For example:

```python
result.evidence
```

Conceptually:

```json
{
  "verified": true,
  "request_id": "req_123",
  "policy_version": "bank-v3",
  "source": "transactions",
  "query_hash": "sha256:...",
  "result_hash": "sha256:...",
  "checks": [
    "identity",
    "authorization",
    "resource",
    "fields",
    "row_policy",
    "query",
    "result"
  ]
}
```

The purpose is NOT cryptographic proof that the LLM is correct.

The purpose is evidence that:

> **The result was produced through a controlled, policy-compliant execution path.**

Be extremely precise about this distinction.

---

# 18. AUDIT LOG

Every request should optionally produce an audit event.

Example:

```json
{
  "event_id": "evt_123",
  "request_id": "req_123",
  "timestamp": "...",
  "actor": "agent:finance",
  "tenant": "bank_a",
  "resource": "transactions",
  "operation": "read",
  "decision": "allow",
  "policy_version": "bank-v3",
  "reason": null
}
```

Audit logging must avoid accidentally logging:

* passwords
* API keys
* raw PII
* sensitive query values
* entire datasets

Provide configurable redaction.

# 23. NATURAL LANGUAGE

Do not make natural-language interpretation part of the trusted layer.

Example:

User:

> "Show me John's transactions."

The LLM can interpret this.

But DataFence receives something structured:

```json
{
  "action": "read",
  "resource": "transactions",
  "filters": {
    "customer_id": "123"
  }
}
```

DataFence validates the structured request.

This keeps the trust boundary deterministic.

# 24. FAILURE MODES

Never silently fall back to unsafe behavior.

Bad:

```python
try:
    safe_execute(...)
except:
    raw_execute(...)
```

Absolutely prohibited.

If validation fails:

```text
DENY
```

or:

```text
REQUIRE_APPROVAL
```

depending on policy.

Security failure must fail closed.

---

# 25. APPROVAL FLOW

Support:

```text
REQUIRE_APPROVAL
```

for sensitive operations.

Example:

```yaml
operations:

      amount_threshold: 10000
```

Then:

```text
Agent
 ↓
DataFence
 ↓
Policy
 ↓
REQUIRE_APPROVAL

 ↓
DataFence
 ↓
Execution
```

Do not build a huge approval UI initially.

Build the primitive and interface.

# 49. NO MAGIC

# 50. VERSION EVERYTHING IMPORTANT

# 51. DETERMINISTIC HASHING

```text

policy
result
```

using cryptographic hashes such as SHA-256.

Do not claim this creates an immutable ledger unless an actual immutable storage mechanism exists.

# 55. FIRST MILESTONE

Your first milestone is NOT:

> "Build an enterprise platform."

Your first milestone is:

> A developer can install DataFence, configure a policy, connect a local SQLite database, submit an agent-like structured request, and receive either an authorized result with provenance/evidence or a deterministic denial.

Example:

```python
from datafence import DataFence
from datafence.connectors import SQLiteConnector

fence = DataFence.from_yaml(
    "banking-policy.yaml",
    connector=SQLiteConnector("bank.db")
)

result = fence.execute({
    "actor": {
        "id": "agent:finance",
        "tenant_id": "bank-a"
    },
    "operation": "read",
    "resource": "transactions",
    "fields": [
        "transaction_id",
        "merchant",
        "amount"
    ],
    "filters": {
        "customer_id": "123"
    }
})

if result.verified:
    print(result.data)
    print(result.provenance)
    print(result.evidence)
```

Then:

```python
result = fence.execute({
    "actor": {
        "id": "agent:finance",
        "tenant_id": "bank-a"
    },
    "operation": "read",
    "resource": "transactions",
    "fields": [
        "card_number"
    ]
})
```

must result in:

```text
DENIED
```

# 58. ENGINEERING RULE

Do not implement fake security.

For example, this is unacceptable:

```python
if "DROP" in sql.upper():

```

because it is trivial to bypass.

```text

```

because a regex detected uncertain language.

Security mechanisms must operate on structured representations wherever possible.

DataFence exists because:

```text
LLMs are probabilistic.
Enterprise data access cannot be.
```

Therefore:

```text
        AI
         │
         │ proposes
         ▼
   ┌─────────────┐
   │  DataFence  │
   │             │
   │  ENFORCES   │
   └──────┬──────┘
          │
          │ executes only
          │ what is allowed
          ▼
    Enterprise Data
```

**The model does not become trusted.**

**The boundary becomes trustworthy.**

Build around that principle.
